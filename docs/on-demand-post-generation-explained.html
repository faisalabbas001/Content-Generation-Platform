1 — The big picture (in one minute)

A brand owner wants one custom post — right now, not as part of the monthly calendar. That is an on-demand post.

The journey is simple to describe:

The client describes what they want on the on-demand page and clicks Generate.
The request is saved to a table called on_demand_requests and handed to the automation engine (n8n).
A chain of AI “agents” builds the post — a Saudi-dialect caption, an image (or video), quality checks, and a safety decision.
One of three things happens: the post is delivered straight to the client, held for a human to review, or it failed.
If it was held, an OGz admin reviews it on the QA screen and either approves (releases it) or rejects it.
An email is sent to the brand owner at the moment their post genuinely becomes available.
The one rule that shapes everything The company has a hard rule: the CEO agent always decides first. Every single generation — calendar or on-demand — is routed through the CEO agent before anything else runs. This is why you will see “CEO” as the very first step of the pipeline.

2 — The client page: /{brand}/on-demand/new

This is the screen at http://localhost:3000/shawarmahousesa-7psz/on-demand/new (the first part of the URL is the brand’s unique slug). It has two parts side by side.

2.1 — The “Brand Context” card (left, read-only)

Before the form, the page shows a small card listing facts it already knows about the brand, pulled automatically from the brand’s profile (its “BrandDNA”):

  • Sector (e.g. food & beverage)
  • Dialect — which Arabic dialect captions should use
  • City, Channel (e.g. Instagram), and the brand Voice

The client cannot edit these — they are shown so the client understands the “defaults” the AI will use. A small < 5 min badge sets the expectation that the post arrives quickly.

2.2 — The form (right)

Deliberately, the form asks the client for almost nothing — only two real choices:

  1. Output type — a simple Image or Video toggle.
  2. The prompt — a single text box where the client describes the post they want, in plain English. It must be between 10 and 5,000 characters.
Hard Rule #3 — Arabic is never typed into the prompt The prompt box is locked to left-to-right (English) input. Arabic text is never sent to the image generator. Instead, the Arabic caption is laid on top of the finished image afterwards. This guide notes this rule again later because it appears in several places.

2.3 — What the client doesn’t fill in (but the system does)

Everything else is filled in automatically so the client isn’t overwhelmed. When the form is submitted it quietly attaches sensible values:

Content typeeducational (a safe default that doesn’t force a particular style)
Objectiveawareness
Platformtaken from the brand’s primary channel (e.g. Instagram)
Canvas / shapederived from the platform (square for Instagram, “snap” for Snapchat)
Colour palettethe brand’s primary colour
Posting time / month“now” / the current month

The same prompt text is used for both the style descriptor and the hero concept the AI works from.

2.4 — What happens the instant the client clicks “Generate”

The form sends the request to the address POST /api/posts/on-demand.
The system checks the client owns this brand (security), then validates every field.
A row is created in on_demand_requests with status queued. This gives the request a permanent ID before anything else runs.
The system signs the request with a secret key and fires it to the n8n automation (the “N8N-A02” workflow), flipping the status to generating.
It immediately replies “accepted” (it does not wait for the post to finish). The page now starts polling for progress.

If the automation engine can’t be reached, the request is marked failed, an anomaly record is logged for the team, and the client sees a friendly error.

2.5 — The live progress bar

While the post is being built, the page checks the status every 2.5 seconds and shows a four-stage tracker:

Validating → Connecting → Generating → Finalizing.

Behind “Generating”, the page shows exactly which agent is working right now, because the automation reports its real step: analysing brand context (CEO) → building caption context (COO) → writing the Arabic caption → quality checks → creating the image → saving. If it takes unusually long (over 2 minutes for an image, 5 minutes for a video), a gentle “this is still working — check back later” message appears, but the work keeps running.

3 — What happens after “Generate” (the AI pipeline)

Once n8n picks up the request, it runs a fixed sequence of specialist “agents”. Each agent is a small AI service that does one job. Think of it as an assembly line:

CEO — classify & route
The CEO agent looks at the brand and the request and decides how to handle it (Hard Rule #1: the CEO always goes first).
COO — compile caption context
Gathers the brand’s tone, dialect and rules so the caption sounds right.
DeepSeek — generate
Writes the Arabic caption and the English “visual brief” (the description the image model will use).
CEO — match chain
Reads what the post is actually about and picks the best visual “chain” (style template + image model). Covered in Section 4.
CCO — quality check (QC)
Scores the result: brand relevance, prompt match, brand consistency, overall quality.
CEO — confidence gate
The safety decision. Outputs one of three verdicts: clean, watermark, or hold.
Image / video generation (FAL AI)
The picture or clip is created. The Arabic caption is then laid on top using image software — never baked into the AI prompt (Hard Rule #3).
Upload to storage
The finished file is downloaded and re-uploaded to the company’s own Supabase storage (Hard Rule #4 — the temporary generator URL is never saved).
Callback
n8n calls back to /api/webhooks/n8n with the message on_demand_complete so the website knows it’s done.
Two hard rules you’ll see in the artwork Arabic overlay (Rule #3): the admin screen actually shows a “clean version (no Arabic overlay)” alongside the final image to prove the rule was followed.
Own storage (Rule #4): only the company’s storage links are ever written to the database.
Reference: the agent services live under apps/web/src/app/api/agents/* — e.g. ceo/classify, coo/compile-caption-context, deepseek/generate, ceo/match-chain, cco/qc, ceo/confidence-gate. The orchestration sequence is described at the top of api/posts/on-demand/route.ts.

4 — How chain selection works

A “chain” is a reusable visual recipe: a style template plus the specific image/video model and settings used to produce it. Example chains: a “Hot Food Hero” chain for steaming dishes, a “Booking CTA” chain for call-to-action posts.

4.1 — Why the chain is picked after the caption is written

The system deliberately does not guess the chain up front. It waits until DeepSeek has written what the post is actually about, then chooses the chain that best fits that real content. Picking a chain before seeing the content would be “blind”.

4.2 — The two related steps

StepWhat it decidesWhen
Select-chains
(monthly calendars)		Only the format (image vs video) and the content type for each slot — not the chain itself.Before generation
Match-chain
(the real chain picker)		Reads each finished post’s actual caption + content and selects the single best-matching chain from the database.After generation, before quality scoring

For an on-demand post, the client just types a free-text prompt and the system picks the chain (and the image model) automatically from that prompt — the client never chooses a chain.

4.3 — The clever part: the rules live in the data, not the code

Self-extending design The chain picker has no hard-coded list of chains. Instead, every chain is a row in the database with its own description — its name, purpose, intent, style affinity, and anti-patterns (what it should NOT be used for). The AI reads those descriptions and reasons about the best match. This means an admin can add a brand-new chain simply by adding a database row — it becomes selectable instantly, with no code changes.

If the AI picker ever fails, the system falls back to a deterministic scoring method so a post is never left without a chain. The chosen chain’s ID and its prompt template are stored with the post and shown on the admin screen.

Reference: apps/web/src/app/api/agents/ceo/match-chain/route.ts (the post-generation picker) and ceo/select-chains/route.ts (format/content-type planner). The note “selection logic lives in the DATA, not here” is in the match-chain system prompt.

5 — The three outcomes: Delivered, Held, Failed

The CEO confidence gate (Section 3) decides which of these happens. The outcome is recorded in the status field of the request.

delivered — straight to the client The post passed all checks. It is written into calendar_posts and becomes visible to the client on their on-demand list and detail page. An email is sent immediately. A clean verdict means no watermark; a watermark verdict means the image is delivered with a watermark applied.
held — sent for human review The CEO gate (or a brand-safety trigger) decided a human must look first. A row is created in the qa_review_queue and the request status becomes held. The post does not appear to the client yet, and — importantly — no “your post is ready” email is sent at this stage. That email only fires later, if and when an admin approves it.
failed — something went wrong The automation couldn’t finish (a timeout, an unreachable service, a quality failure, or a hard safety block). The status becomes failed and a plain-language reason is shown to the client, who can edit the prompt and try again. The raw technical reason is kept for support but never shown directly to the client.

The safety net

When n8n calls back with on_demand_complete, the website performs a careful “safety-net” update: it only flips a request to delivered if it was still generating. This guarantees it can never accidentally overwrite a “held” post and email the client about something a human hasn’t approved yet.

Reference: outcome handling in apps/web/src/app/api/webhooks/n8n/route.ts (search for on_demand_complete); the status values are defined by the on_demand_status_type enum in supabase/migrations/0044_on_demand_requests.sql.

6 — The database: every table & field, and why

Five tables do the heavy lifting. Here is each one in plain terms, with what every field is for.

6.1 — on_demand_requests — the client’s brief & the request’s life story

Why it exists: the normal product is a monthly calendar of ~20 posts. An on-demand post is a single, one-off request with a custom brief that doesn’t fit the monthly structure — so it gets its own table. This table captures the brief, tracks the request end-to-end, and links to the post that eventually gets produced.

FieldPlain-English meaning
request_idThe unique ID for this request (the page URL uses it).
brand_idWhich brand this belongs to.
content_type, objectiveWhat kind of post and its goal (e.g. educational / awareness).
media_typeImage or video (added later, defaults to image for old rows).
platform, canvasWhere it’s for (Instagram, Snapchat…) and its shape/aspect ratio.
posting_time, month, posts_per_weekScheduling hints.
occasion_name, occasion_lead_weeks, occasion_priorityOptional event the post ties to (e.g. National Day).
hashtagsRequested hashtags.
style_descriptor, hero_conceptThe visual brief — comes from the client’s prompt (English only, Rule #3).
negative_promptWhat the image should avoid.
cultural_guidanceCultural notes for the post.
color_paletteBrand colours to use (hex codes).
image_model_prefPreferred image engine, or auto to let the system choose.
first_ever_postFlags a brand’s very first output (auto-held for an extra quality check).
overlay_brand_name_arWhether to overlay the Arabic brand name on the image.
statusThe life story: queued → generating → delivered / held / failed.
current_stepThe live pipeline step (ceo, coo, caption, qc, image, upload, done) — powers the progress bar.

Security: a client can only read and insert their own brand’s requests; clients can never update the status directly — only the automation (using a service-role key) can. This is enforced by database rules (RLS).

6.2 — calendar_posts — the actual finished post

This is the shared table for every post, whether it came from a monthly calendar or from an on-demand request. On-demand changes added a few things:

FieldPlain-English meaning
calendar_idMade optional — on-demand posts have no monthly calendar.
on_demand_request_idLinks the post back to its on-demand brief.
route_decisionThe CEO gate verdict made explicit: clean, watermark, or hold.
revision_countHow many times the client has regenerated this post (capped at 3).
storage_url, clean_storage_urlThe final image/video, and the “no Arabic overlay” clean version.
caption_ar, hashtagsThe Arabic caption and tags.
confidence_score, watermarkQuality score and whether a watermark was applied.
statusWhere the post is in its own approval life (e.g. pending when released to the client).

Built-in safeguard: a rule guarantees every post belongs to exactly one parent — either a monthly calendar or an on-demand request, never both and never neither.

6.3 — admin_regenerations — the admin’s private “draft lane”

Why it exists: when an admin regenerates a post, the new version must not be shown to the client until the admin approves it. So admin regenerations live in their own table as “drafts” and never touch the live post until promoted.

FieldPlain-English meaning
regen_idUnique ID of this draft version.

media_type, storage_url, clean_storage_urlThe draft’s media files.
caption_ar, hashtags, confidence_score, watermarkThe draft’s caption, tags and scores.
prompt_overrideIf the admin edited the prompt, the custom prompt used.
image_modelWhich model produced this draft.
statusdraft → approved / rejected / superseded (replaced by another approved version).
created_by, reviewed_by, created_at, reviewed_atWho made/decided it and when.

Security: this table is admin-only at the database level — clients have no access whatsoever, so admin drafts can never leak.

6.4 — qa_review_queue — the “needs a human” list

When a post is held, a row is added here. This is what populates the admin QA screen.

FieldPlain-English meaning
queue_idUnique ID of the review item.
post_id, brand_idWhich post and brand.
statuspending → approved / rejected.
trigger_reasonWhy it was held (the hold reasons — see Section 7.4).
cco_score, flagsThe quality score and detailed flags (brand relevance, prompt match, etc.).
resolved_at, reviewed_atWhen it was decided.

6.5 — Supporting tables

  • usage_logs — an audit trail; every webhook callback and every admin approve/reject is recorded here.
  • anomaly_records — logged when something abnormal happens (e.g. the automation engine is unreachable).
  • brand_profiles — the brand’s identity and the owner’s account, used to find the email address.
  • calendars — monthly calendars (used to look up the month for emails when relevant).

7 — The admin review screen: /admin/qa?tab=on_demand

This is the OGz team’s quality-assurance (QA) desk at http://localhost:3000/admin/qa?tab=on_demand.

7.1 — The two tabs

The QA page has two tabs, each showing a count of items waiting:

  • Calendar — held posts from monthly calendars.
  • On-Demand — held posts from on-demand requests (the focus of this guide).

The On-Demand tab shows a paginated grid of brand cards (10 per page) — one card per brand that has on-demand activity. A small “new” badge signals fresh arrivals. Clicking a brand opens that brand’s on-demand items, and clicking an item opens the full inspection page.

7.2 — The inspection page layout

The inspection page is a two-column workspace built to give a reviewer everything in one place.

Left column — four tabs

TabWhat it shows
PreviewThe generated image or video, the “clean version” (no Arabic overlay, proving Rule #3), the Arabic caption (shown right-to-left), the hashtags, and a strip of regenerated versions.
DeepSeek DataEverything the AI produced: the client’s original prompt, the English image prompt (with a green “Arabic-clean” badge or a red warning if Arabic slipped in), the negative prompt, the chain template and chain ID, cultural guidance, a metadata grid (content type, format, platform, route decision, watermark, model, confidence mode, occasion), the colour palette, and the request ID.
CCO / FlagsThe quality scores and a detailed breakdown of every hold reason, plus the raw flag values.
Revision HistoryEvery admin regeneration draft for this post, each with its version, time, image, caption, scores and status.

Right column — facts & actions

  • IDs card: Post ID, Queue ID, Request ID, and created date.
  • Score cards: CCO Score, Visual QC, Brand Relevance, Prompt Match, Brand Consistency. A dash (“—”) means that check didn’t run — scores are never invented.
  • Quick meta: Route, Chain, Format, Platform, Watermark, Model — colour-coded (green = clean, amber = watermark, red = hold).
  • Hold reasons summary: badges showing why it was held.
  • Action suite: the Regenerate button and the Approve / Reject buttons.

7.3 — Selecting a regenerated version

When a reviewer clicks a draft version in the history strip, the entire page re-renders to show that version — its image, caption, prompts and model — so they can compare versions exactly as they’d see the original. (The original AI quality scores don’t apply to a draft, so those simply show “—” for a selected draft.)

8 — Regeneration (client side & admin side)

Both the client and the admin can ask the system to “try again”. They use the same automation workflow (N8N-B03), but with one crucial difference — a target flag — that completely changes the outcome.

8.1 — Client regeneration (target = user)

On their on-demand detail page, a client can click Regenerate (optionally with a custom prompt). Then:

  • The system first checks the post hasn’t already been regenerated 3 times (the cap). If it has, it stops and says so.
  • N8N-B03 runs the full pipeline and overwrites the live post in place, bumping revision_count by one.
  • Because the live post changed, the new image is immediately visible to the client, and a “your image is ready” email is sent.

A regeneration can itself come back held (sent to admin review) or rejected (blocked by the brand-safety gate) — the client sees a clear message for each case.

8.2 — Admin regeneration (target = admin)

On the inspection page, an admin clicks Regenerate and chooses one of two options in a modal:

  • Use Existing Prompt — re-run with the same prompt.
  • Edit & Regenerate — refine the prompt first (English only).

The critical difference: the admin’s result does not overwrite the live post. Instead it is saved as a new draft in admin_regenerations — invisible to the client — and appears in the version-history strip. The admin can generate several drafts and compare them. A live progress tracker (Queuing → Connecting → Running AI generation → Saving draft) mirrors the real pipeline step by polling the admin status endpoint.

Why two completely separate paths? The client’s own regeneration history (live post + revision_count) is kept entirely independent from the admin’s draft history. This way an admin can experiment freely without ever disturbing what the client currently sees.
Reference: client path apps/web/src/app/[slug]/on-demand/actions.ts → requestRegenerate · admin path apps/web/src/app/actions/admin-regenerate.ts → requestAdminRegenerate · admin button UI admin/qa/admin-regenerate-button.tsx · admin progress endpoint api/admin/on-demand/[requestId]/status/route.ts · workflow n8n/flows/N8N-B03_ Revision Request Handler.json.

9 — Approve, reject & hold — what each button really does

The inspection page has two different kinds of approve/reject. It’s important not to confuse them.

9.1 — Approving / rejecting the held item itself

These are the big Approve / Reject buttons in the bottom-right action suite. They decide the fate of the original held post:

  • Approve releases the held post to the client and resolves the queue item. (Disabled for a Hard Block.)
  • Reject declines it. Both actions ask for confirmation and are recorded in the audit log.

9.2 — Approving / rejecting an admin draft version

Inside the version-history strip, each admin draft has its own “Approve this version” and “Reject” controls. Approving a draft is the moment a private draft becomes the live post. Here is exactly what “approve a draft” does, step by step:

Promote the draft into the live post. The draft’s image, caption, hashtags, score and watermark are copied into calendar_posts, and the post’s status is set to pending.
Reveal the request. The on_demand_requests row is marked delivered so the client can see it.
Tidy the drafts. This draft is marked approved; any other open drafts for the same post are marked superseded.
Close the queue item. The matching qa_review_queue row is marked approved and leaves the queue.
Record & notify. The decision is written to the audit log, and the “post approved” email is sent to the client.
Important nuance: “admin approval = release, not final approval” When an admin approves, the post is released to the client with status pending — meaning the client then approves it (or requests a revision) from their own calendar. Admin approval makes it visible; the client still has the final say on their own content.

Rejecting a draft simply marks that draft rejected. It stays in the history for the record, and nothing the client sees changes — they keep seeing the last approved asset.

Reference: held-item actions apps/web/src/app/actions/qa.ts → approveQaItem / rejectQaItem · draft actions apps/web/src/app/actions/admin-regenerate.ts → approveAdminRegeneration / rejectAdminRegeneration.

10 — How email notifications work

Emails are sent through a shared helper called notify(), which uses Resend as the email provider. The system is careful to email the client only at the genuine moment a post becomes available — never before.

10.1 — When an email is (and isn’t) sent

EventEmail sent?Which template
Post delivered straight awayYes — immediatelypost_approved
Post held for reviewNo — held posts wait for an admin—
Admin approves a held post / draftYes — at the moment of approvalpost_approved
Client regeneration succeedsYes — “new image is ready”post_approved
Post failedNo email — shown on screen instead—

Notice the same post_approved (“your post is ready”) template is reused across all the “it’s available now” moments, so the client gets one consistent message.

10.2 — How the right person is found

To send the email, the system looks up the brand to find the owner’s account, then resolves that account’s email address. The email is personalised with the brand name, the post’s position, and the month (taken from the post’s calendar, or from the request’s posting time for on-demand posts).

A subtle but important technical choice These emails are sent “awaited” (the code waits for the send to complete) rather than fire-and-forget. On serverless infrastructure, a fire-and-forget send can be killed before it finishes, leaving the notification stuck. The notify() helper also never throws an error, so a hiccup in email can never break the post itself.

10.3 — Internal alerts (not to clients)

Separately, when an anomaly is routed for human attention, the relevant internal “copilot” (tech, management, or production) receives a direct alert email so the team can act quickly. These go to staff, not clients.

Reference: delivery email api/webhooks/n8n/route.ts → fireNotifyOnDemandDelivered · client-regeneration email [slug]/on-demand/actions.ts → fireNotifyOnDemandRegenerated · admin-approval email actions/admin-regenerate.ts → fireNotifyApproved · the notify() helper and templates live in @repo/email.
