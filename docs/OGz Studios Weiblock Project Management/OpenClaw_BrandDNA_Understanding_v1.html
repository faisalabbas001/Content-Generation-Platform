01What's shifted — old understanding vs new

The original doc.txt spec defined BrandDNA as a 10-field "BrandDNA Lite" identity: dialect, formality, religious sensitivity, price position, etc. That schema is still the foundation — none of those fields go away. What v2 of the framework adds is a second layer above it: creative direction — the deliberate composition of voice, diagnostic, visual idiom, cadence, and closing pattern that makes a brand's content feel like that brand instead of generic Saudi-SME content.

Concept Original understanding New understanding (v2)
BrandDNA scope 10 critical identity fields per brand. 10 identity fields plus a creative-direction layer (archetype × lifecycle × intent → composed method profile).
Voice / tone One free-text "brand_differentiator" + tone anti-attributes. Voice register is one of 5 method-anatomy components, separately addressable, sourced from any of 6 methods.
Method assignment Implicit. COO inferred a generic tone from form + scrapers. Explicit. The Composition Matrix scores 6 methods against the brand's (archetype × stage × intent) tuple and picks one or composes a hybrid.
Archetype Not modelled. One of 12 Jungian archetypes. Primary required, secondary optional. Drives 70% of voice signal.
Lifecycle stage Not modelled. One of 5 (Launch, Growth, Maturity, Transition, Renewal). Inferred mostly from Instagram + website signals.
Intent state Implicit in primary_kpi_type + occasion logic. Explicit field with 5 enum values. Most fluid — can change month to month.
Onboarding form 21 fields, single screen. 3 sections with explicit dependencies: Section 2 needs scrape data from Section 1 to be useful.
Important — this is not a contradiction with doc.txt

The new framework extends Family A; it doesn't replace anything. The 4 Hard Rules (CEO routes first, Memory Controller is the sole writer, Arabic never in image prompts, no Weavy URLs in DB) all still apply. The 11 n8n flows still exist with the same purpose. What changes is what COO produces during onboarding and what fields BrandDNA carries forward.

04Methods as composable patterns

This is the architectural shift v2 of the framework introduces. The change in one sentence:

A method is not a person and not a monolithic style. A method is a composed instruction set with five independently classifiable components. Each component is separately addressable, separately swappable, and can be sourced from different methods simultaneously.

The framework explicitly says: Vulnerability is the highest-leverage addition possible in Phase 1. But it must be built after the composable architecture exists, not before. Building Vulnerability first means rebuilding it once the (archetype × stage × intent) plumbing arrives.

05The Composition Matrix — auto-method-selection

For every (archetype × lifecycle_stage × intent_state) triple — 300 total combinations — the system scores all 6 methods 0-100 and either picks the single top scorer (clean assignment, ~180 of 300 cases) or composes a hybrid by taking specific components from multiple methods (~120 cases).

Where no method scores above 80, the system falls back to composition — pulling the highest-scoring component for each of the five method-anatomy slots from whichever methods are strongest in that dimension.

07The 3-section onboarding form

We propose splitting the existing 21-field single-screen form into three sequenced sections. The reason isn't UX cosmetic — it's technical dependency: Section 2 needs the scrape data from Section 1 to be useful, and Section 3 needs both. This sequencing is what makes "extraction first" architecturally enforced rather than just polite.

1

Section 1 — Identity & data sources

The minimum we need to start scraping. Submitting this section kicks off Apify, the website scraper, and Google Places in the background while the user fills the next section.

Fields: brand_name_ar, brand_name_en (optional), sector, city_primary, instagram_handle, website_url, place_search.name.

Estimated time: ~45 seconds.

2

Section 2 — Voice & identity confirmation

Pre-filled from extraction. The user reviews and corrects rather than types from scratch. If extraction returned high-confidence values (e.g. dialect detected from Instagram captions), those are pre-selected; the user clicks to confirm or change.

Fields: arabic_dialect (pre-filled), price_position, brand_differentiator, formality_level, humor_tolerance, religious_sensitivity, bilingual_ratio, tone_anti_attribute_ids, primary_color_hex, logo upload.

Estimated time: ~2-3 minutes.

3

Section 3 — Audience & intent

Strategic intent + occasion priorities + audience mix. This section drives intent_state directly and feeds the Composition Matrix.

Fields: primary_channel, primary_kpi_type, intent_state (new dropdown), audience gender mix, 5 occasion relevance selects.

Estimated time: ~1-2 minutes.

Why this ordering matters technically

Today, the form submit fires N8N-A03 with everything at once. That means the user types things like "Instagram handle" and then has to wait 60-90 seconds on a processing screen before seeing anything. With the 3-section split, scraping happens during Section 2 — the user is already moving forward while Apify runs. By the time they reach Section 3, the data is back, and Section 3's voice/intent questions can be informed by what we already know.

08Dependency order — why extraction comes first

When we sequence the build work, certain things must land before others or downstream changes break. This is the order we propose:

#StepDepends onWhy this order
1 Schema migration: add 4 new fields to brand_profiles + new brand_method_profiles table — COO has nowhere to write until columns exist.
2 Pattern catalog: enums for the 5 method-anatomy components step 1 COO output can't be validated without a closed enum.
3 Apify config update: capture post timestamps for lifecycle inference — Without timestamps, COO can't tell Launch from Growth from Maturity.
4 Onboarding form refactor: 3 sections + Section 1 background-extraction trigger step 3 Form must call the right pre-extraction endpoint.
5 COO prompt rewrite: add archetype, lifecycle, intent inference + Composition Matrix + 5-component output steps 1, 2, 3 Prompt depends on knowing what schema, enum, and signals are available.
6 Memory Controller whitelist update + recompute critical-fields constant (12 fields, not 10) step 1 Existing field_update path must accept the new field paths.
7 UI updates: snapshot/profile/admin show archetype + method profile steps 1, 5 Display depends on data shape being final.
8 CCO + DeepSeek prompts: consume method profile in CaptionContext step 5 Downstream chains can't use what doesn't exist yet.
9 Vulnerability Method (the 6th method) added to the matrix and prompts steps 1-8 Build the method into a working architecture, not the other way round.

09Edge cases & questions for you to verify

These are the cases that aren't obvious from the framework document and that we need your call on before we lock the schema and prompts. Each one has our proposed answer and what it would cost to do something different.

Q1

What if the user has no Instagram account?

Roughly 15-20% of Saudi SMEs we'd onboard don't have a meaningful Instagram presence (new businesses, B2B, government suppliers). Without Instagram we lose our richest archetype and lifecycle signal source.

Our proposed answer:

  • Mark Section 1's instagram_handle as optional (already is).
  • If empty: COO falls back to website-only + Google Places + form answers. Confidence floor for archetype caps at inferred_medium (never inferred_high) — we never claim certainty without two sources.
  • Lifecycle defaults to Launch for any brand with no Instagram, no website, and account creation date < 12 months. If the user pushes back, we add a manual lifecycle dropdown to Section 3.
  • Section 3 adds a confirmation question: "We couldn't find an Instagram for your brand — is that intentional?" Helps us tag B2B vs new vs intentional-low-presence.
Verify with client: is the Launch-default acceptable, or do you want a manual override always shown when Instagram is missing?
Q2

What if Google Places returns zero results?

Pure-online brands (e-commerce, SaaS, services without physical location) won't have a Places record. Currently the scraper branch silently skips with no fallback signal.

Our proposed answer:

  • Treat "no Places result" as a positive signal for online-native, not a missing-data failure.
  • The COO prompt receives places_extraction: null with a flag {"online_native": true} attached.
  • Online-native brands get a slight bias toward Explorer/Magician archetype, Growth or Launch lifecycle, and Conversion-Promotional intent unless other signals contradict.
Verify with client: are there sectors where missing Places should block onboarding (e.g. F&B that must have a physical location)? If yes, we add a sector-specific check.
Q3

What if the website returns 0 useful signal? (404, password-protected, single-page coming-soon)

This is more common than expected — many SMEs have an SSL'd holding page or Linktree-style URL. The website scraper returns HTML but no extractable signal.

Our proposed answer:

  • Detect via heuristics: HTML < 5KB, no <p> tags, no meta description, only "coming soon" / "under construction" keyword detected.
  • If detected: pass website_extraction: { has_website: true, content_extracted: false, reason: "holding_page" } to COO.
  • Lifecycle inference biases toward Launch if Instagram also confirms early-stage.
  • Don't penalize completeness_score — the user did provide a URL, they just don't have content yet.
Verify with client: should we surface this in the snapshot ("Your website needs content — here's what we'd recommend") as part of the BrandDNA report?
Q4

What if Instagram is in a non-Arabic language? (English, mixed, emoji-only)

Arabic dialect is the highest-leverage BrandDNA field. If Instagram captions aren't in Arabic, we lose our single best dialect signal.

Our proposed answer:

  • If > 70% of captions are non-Arabic: dialect_confirmed = false, mark arabic_dialect as missing regardless of form answer until user confirms.
  • Section 2 form shows the dialect question with extra prominence and a note: "We couldn't auto-detect this from your Instagram. Please confirm."
  • This blocks A01 auto-trigger (the gate already requires dialect_confirmed).
Verify with client: is "user confirms manually" sufficient, or should we send the captions to a separate dialect-classifier model first?
Q5

What if extraction returns conflicting signals? (form says "Najdi", Instagram says "Hejazi")

The framework treats this as a real signal — disagreement between sources is information. But the system needs to handle it somewhere.

Our proposed answer:

  • Memory Controller already supports conflict_flag on evidence bundles. We use it.
  • COO Pass 2 marks the field as inferred_low with conflict_flag = true.
  • The brand falls into confidence_mode = Cautious for that field.
  • Section 2 surfaces a "We see disagreement here — please confirm" prompt with both options visible.
  • Logged to branddna_event_log as contradiction_detected.
Verify with client: is the Cautious-mode-with-prompt the right behavior, or should we hard-block until resolved?
Q6

What if archetype detection scores below the confidence floor?

We require inferred_medium minimum on archetype. If signals are weak enough that COO can't reach that floor, we have to do something safe.

Our proposed answer:

  • Default to the most common archetype for the brand's sector (Caregiver for healthcare, Sage for finance, Everyman for F&B, etc.).
  • Mark as inferred_low with a flag for human review.
  • Surface in /[slug]/profile under "Archetype" with a "Confirm or correct" prompt — same correction flow as other low-confidence fields.
Verify with client: sector-default archetype map below — please confirm or correct.

Q7

What if all 6 methods score below 80 in the Composition Matrix?

The framework calls these "GAP" cases — they require composition. We need a policy for what composition means in code.

Our proposed answer:

  • Take each of the 5 method-anatomy components independently.
  • For each component, pick the highest-scoring method's pattern for that slot. Different methods can win different components.
  • Set composition_score to the average of the winning component scores.
  • If average < 60: flag for human review (Production Copilot picks it up).
Verify with client: 60 floor reasonable, or should it be tighter (70+)?
Q8

How does intent_state change over time, and who triggers the change?

The framework calls intent_state "the most fluid axis — can shift month to month." But who decides the shift, and when does the system pick it up?

Our proposed answer:

  • Default path: intent_state set at onboarding stays until the user changes it via /[slug]/profile (correction form).
  • Auto-suggest path: N8N-A05 (monthly cycle) detects when current intent's chain-mix is producing low CCO scores and suggests an intent change. This goes to Production Copilot for human approval.
  • Calendar override: user can pick a different intent for a single calendar via the calendar generation UI (e.g. "this Ramadan calendar should be Awareness-Attraction even though my default is Differentiation-Loyalty"). Per-calendar override doesn't change the brand default.
Verify with client: is the per-calendar override important to launch, or can it wait for Phase 2?
Q9

How do existing brands (already in DB before this v2 ship) get backfilled?

Today's brand_profiles rows have no archetype, no lifecycle, no method profile. They'll all be NULL after migration. What's the right backfill?

Our proposed answer:

  • One-time backfill script: for each existing brand, run COO Pass 2-4 once using their existing form data + any cached scraper output in source_records.
  • Mark all backfilled values as inferred_medium max — we never claim certainty on a backfill since we may not have current data.
  • Surface in admin Branddna inspector with a "Backfilled — needs review" badge for ops to walk through.
Verify with client: acceptable, or do you want existing brands to re-run the full extraction (more accurate but costs API credits per brand)?
Q10

What about secondary archetypes — when do we set them?

The framework supports dual-archetype brands but doesn't say when secondary is appropriate vs noise.

Our proposed answer:

  • Set archetype_secondary only when:
    • Two archetypes both score above 60 in COO's signal-matching, AND
    • Their combined score > 140, AND
    • The gap between #1 and #2 is < 15 points.
  • Otherwise leave NULL. A weak secondary is worse than none — it dilutes content direction.
Verify with client: threshold reasonable, or should it be tighter?
Q11

How do we display the new fields to the end user?

The user might not know what "archetype" or "Vulnerability Method" mean. Showing raw enum values would feel like jargon.

Our proposed answer:

  • /[slug]/snapshot: show archetype as a friendly label with a 1-line description ("The Caregiver — your brand serves and protects"). Show method as the creative_direction_text COO writes — that's already plain language by design.
  • /[slug]/profile: shows component-level breakdown for users who want to drill in. Each of the 5 components has a short tooltip.
  • /admin/branddna/[brand_id]: shows raw enums + composition_score + composition_blend JSON for ops debugging.
Verify with client: do you want to use Arabic translations of the archetype names, or keep English-only on the front-end?
Q12

What does the snapshot UI show during the extraction wait (Section 1 → Section 2)?

The 30-60 second extraction window is dead air for the user if we don't fill it.

Our proposed answer:

  • While Section 2 form is loading: show a real-time "We're looking up your brand…" panel with 3 progress lights (Instagram, Website, Google Places).
  • As each scraper returns, the corresponding light flips green AND the relevant Section 2 fields get pre-filled.
  • If a scraper returns nothing useful: that light goes amber and the field stays empty. User fills manually.
Verify with client: is this UX acceptable, or do you want us to skip the per-scraper detail and just show "Loading…"?

10Agent prompts we need from you (resend / revise)

The new framework changes what each AI agent must produce. The current prompts in our prompts/ folder were authored against the original doc.txt — they don't reference archetype, lifecycle stage, intent state, the Composition Matrix, the 5-component method anatomy, or the Vulnerability Method. We need updated prompts from you, written in the same authoritative voice and structure as the originals you provided, so we can drop them in via SEC-06 (env-only, never source-code).

What we cannot do without your re-sent prompts

We can wire the schema, the data flow, and the composition logic ourselves. But the creative judgment encoded in the prompt — how COO detects archetype from caption tone, how it scores Vulnerability vs Authenticity, how it writes the creative-direction brief in your house voice — must come from you. If we generate prompt text ourselves we'll drift from your editorial intent, and the BrandDNA outputs will reflect our voice, not yours.
