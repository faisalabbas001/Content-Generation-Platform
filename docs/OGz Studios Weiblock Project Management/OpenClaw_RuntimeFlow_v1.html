The Runtime Decision Flow

From generation trigger to scheduled post — the complete decision graph for how OpenClaw produces a single piece of content. Six stages, six decision diamonds, every shape mapped to a code module a programmer can implement directly.

The shape vocabulary

Every shape in the diagram below carries a precise meaning. Programmers reading this diagram should be able to map every element to a corresponding code module, table, API call, or agent prompt without ambiguity. This is a build spec, not decoration.

Shape semantics
Pill / Capsule
Entry and exit points of the flow
Rectangle
A function or processing step
Diamond
A yes/no or branching decision
Cylinder
A Supabase table or storage
Parallelogram
External API or system boundary
Hexagon
CEO, COO, CCO agent invocation

The CEO agent is the entry point for every runtime generation, but it is not the start of the diagram. The trigger fires first — weekly batch, on-demand, or occasion auto-trigger — then control passes to the CEO agent. This distinction matters because the trigger determines what the CEO agent reads first.

The runtime flow

One generation. From trigger to scheduled post. Six diamonds carry the decision logic. Every box maps to an executable module.

Notice the two dashed red loops in the lower diagram. The CCO rejection loop (Diamond 5) writes to Family D and regenerates with stricter constraints. The client revision loop (Diamond 6) writes to Family D and routes back to Stage 4 with new method-composition constraints. These are not error paths. They are the learning paths. Every loop fired makes the system smarter for that brand specifically.

The six stages in implementation terms

Each stage maps to a discrete code module a programmer implements independently. The interfaces between stages are the system's natural boundaries — these are where Weiblock can split the work, parallelize the build, and test in isolation.

STAGE 01
Trigger
Three entry points converge into the CEO agent. Each trigger carries a payload identifying the brand, the requested chain (or null for auto-selection), and any context flags from the calling system.
Modules: N8N-A01 (cron), N8N-A02 (webhook), N8N-A03 (calendar listener)
Output: trigger_event {brand_id, chain_id?, occasion_id?, force_regenerate?}
STAGE 02
CEO agent reads BrandDNA
CEO agent invokes the master read function which assembles all five families with the read-order priority applied. This is the single source of truth for everything downstream — no other module reads the families directly.
Module: getBrandDNA(brand_id) → composed BrandDNA object
Read order: Family B → A → E → D → C
Output: BrandDNA composite + confidence_score
STAGE 03
Chain selection
CEO agent decides which chain runs in this slot. Reads intent state mix percentages, occasion calendar, and last N posts to avoid repetition. Returns a chain_id and the chain's metadata record.
Module: selectChain(intent_mix, occasion, last_n_chains, force_chain?)
Output: chain_record + requires_ref_image flag
STAGE 04
Method composition
COO agent runs the (archetype × stage × intent) lookup against the method matrix. Returns either a single method assignment or a composed hybrid pulling patterns from the top three scoring methods. Diagnostic always runs upstream.
Module: composeMethod(archetype, stage, intent) → method_or_hybrid
Output: resolved prompt template + register + anti-patterns
STAGE 05
Generation execution
N8N-V01 routes to sync or async based on chain's format tier. Sync calls fal.ai and waits. Async submits, polls every 5-8 seconds, retrieves URL when complete. Sharp applies Arabic overlay. File uploads to Supabase Storage. CCO reviews against Policy.
Module: N8N-V01 (visual generation workflow)
External: fal.ai REST API · Supabase Storage
Output: artifact_url + generation_log entry
STAGE 06
Caption + approval
DeepSeek V3 generates 3 caption variants. CCO filters any that fail policy. Client sees the surviving variants in the dashboard, picks one or revises. Approved posts queue for publishing. Revisions write to Family D and loop back.
Module: generateCaptions(artifact, BrandDNA) + dashboardApproval
External: DeepSeek V3 API · Postiz queue
Output: scheduled_post + Family D learning record

The six decision diamonds

The diamonds carry the system's logic. Every other shape is execution. These six decisions are where the platform actually thinks. Programmers implement each as a discrete function with explicit inputs and labeled outputs.

# Decision question Function signature YES path NO path
01 Brand confidence ≥ 75? checkConfidenceGate(brandDNA) Full pipeline runs Safe mode: watermark + simpler chains only
02 Chain requires reference image? chain.requires_ref_img Fetch from Family C → validate via Sharp Route to AI-only generation path
03 Top method scores ≥ 80? scoreMethods(archetype, stage, intent) Single method assignment Hybrid composition from top 3 methods
04 Sync or async generation? chain.format_tier > 1 Async: submit + poll + retrieve Sync: direct call + wait
05 CCO approves output? ccoReview(artifact, policy) Proceed to caption generation Log violation + regenerate with constraints (loop)
06 Client approves variant? dashboardDecision(post) Schedule for publishing + write Memory Capture reason + write Memory + loop to Stage 4
